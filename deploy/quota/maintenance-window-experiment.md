# 裁剪恢复维护窗口：隔离演练记录

**仅供审查和独立合成环境演练，不能据此操作客户环境。** 实验工作树已用实际条件核验取代字面量硬关闭；该候选尚未通过独立复审或端到端验证，不得用于生产。本文不是生产恢复指令，不得手动删除锁或重试未知任务。

## 适用边界

演练对象必须是事先创建的专用虚拟机和合成 ext4 卷，记录虚拟机身份、卷设备号和挂载点、容器完整 ID、镜像 ID、单元文件与哈希，并确认没有用户数据、生产凭据或宿主 Docker socket。正式部署必须另行建立与部署、账本和卷绑定的清单并独立验收；不能复用演练身份或根据路径相似就认定目标相同。

依赖受信运维维护合同：从检查前到完全恢复期间，运维及外部自动化不得创建或启动其他写者、重启已屏蔽服务、改变挂载/命名空间或使用旧 Docker API；所有已知入口必须枚举并停用。该合同不声称能阻止有权限的管理员故意违反。无法确认合同、入口或卷身份时停止。尤其不能假定单个 PID 的消失、单次 `/proc` 扫描或某一挂载点卸载成功意味着所有旧引用已消失。

## 待现场核验的步骤

1. 记录原始状态：专用卷设备及真实挂载、数据目录/数据库文件身份、所有服务和定时器的 active 与 enable/mask 状态、容器完整 ID、挂载和 restart policy、相关命名空间；记录镜像版本与配置，准备并独立验证一致性备份。核对已知应用、配额 helper、worker、socket、daemon、定时器、容器和外部自动化入口，任何未知入口或其他数据卷混用均停止。
2. 阻断请求并按照依赖停止已知写者，屏蔽其自动启动入口；逐项读回 inactive 与 masked 状态，验证旧应用、socket、daemon、容器和进程已退出。系统服务或自动化仍可能创建写者时不能继续；不得停止共享 Docker 来代替仅停止专用组件。
3. 按设备身份枚举所有可核验的挂载命名空间及其挂载、绑定别名，检查目标卷的 FD 和共享映射，任何未知写者、不可读或无法归属项均停止。FD 和映射扫描不是完整证明：已排队的 SCM_RIGHTS 可以持有未列出的文件句柄，无进程但被固定的命名空间也可能不在普通 `/proc/<pid>/mountinfo` 清单中。必须在具体环境独立证明这些入口已关闭；不能仅靠扫描通过。
4. 在每个已核验命名空间中，对每个目标卷挂载进行**非 lazy**卸载，遇 busy、失败、未知别名或状态变化立即停止并保留证据；复核所有已知挂载均不存在，并核验已知服务没有直接使用该块设备的入口。只卸载宿主路径不够。相关引用的完整性或并发屏障无法证明时不得进入恢复操作。
5. **实验中的维护挂载方式**：所有已知旧挂载及写者均已处理后，在私有 mount namespace 内，将事先核验的同一合成设备挂载到该 namespace 内的原数据路径；宿主同路径不挂载原卷。再次核验设备、数据目录及 SQLite 的设备号/inode 和实际配置，再逐可见 namespace 确认卷只在维护 namespace 出现，复核旧服务始终 inactive/masked 和运维合同仍生效。在维护 namespace 中获取同一文件系统的锁并验证 SQLite 能打开；不得根据文件路径相同推断文件相同。维护完成后先关闭数据库与锁，在该 namespace 非 lazy 卸载，再检查无旧挂载，方可依原记录恢复宿主。任何身份不符、锁不可用、挂载或卸载失败、未知 namespace、状态变化立即停止。
6. 恢复 CLI 候选已经改用实际条件核验；在完整部署身份、写者隔离、数据库和任务终态、崩溃恢复与独立复审均未通过前，不得执行。上一步仅证明操作系统原语，**未证明现有 CLI 的 identity/fence、专用 Docker 和数据库事务能在此 namespace 中共同通过**，不得拿原语演练替代真实 CLI 验收。维护过程中状态未知时，保留原卷、账本、锁和审计记录，不清理任务、不覆盖数据。
7. 依原始记录逐项恢复：先核验同一卷和数据库身份及一致性，再恢复挂载、quota 和应用及原有启动策略，核实容器与原状态一致；已停止的回滚容器保持停止。复核服务健康、读写路径和用户结果，再恢复入口。恢复失败则保持入口关闭，记录具体失败；不要把自动重启当作成功。`mask --runtime` 在重启后不持久，重启或断线必须重新核验整个维护窗口。

## 已有隔离证据与缺口

独立 Linux VM、合成 ext4 卷和专用测试单元中：停止并屏蔽模拟 app、quota、mount 后，模拟 app 重启被拒；旧命名空间持有 FD 时非 lazy 卸载失败，关闭 FD 后成功。复核当时 10 个可见命名空间没有该卷挂载；恢复后卷、app、quota 运行，三个停止的回滚容器仍停止，合成内容未变化。将维护进程在服务及挂载已屏蔽、停止后 SIGKILL，屏蔽仍在；手工恢复后状态一致。另一次使用同一合成 ext4 设备，在私有维护 namespace 的原路径重新挂载：SQLite 设备号/inode 不变，持有独占 flock 并开启 SQLite 写事务；宿主原路径不可见，该时点扫描 10 个可见 namespace 仅维护 namespace 有目标挂载。释放锁与事务并卸载后，原始模拟服务状态恢复。日志 `/tmp/trim-rh-remount-fixed-result.log`。以上仅覆盖合成运行和一个崩溃阶段。

独立负例：同一命名空间内 FD、MAP_SHARED 和 SCM_RIGHTS 排队引用会使对应挂载点卸载报 busy；但宿主卸载成功后，其他命名空间中的旧 FD 仍可写，另一个 bind 挂载仍可访问；私有命名空间内移动挂载不会移除宿主挂载。单独打开的块设备也不受文件系统挂载点卸载约束。测试脚本及日志只在任务专用 VM 的 `/tmp/trim-rh-*`、`/tmp/trim-ext4-*` 和 `/tmp/trim-window-*`，并非安装产物。

同一合成维护窗口中，真实 `verifyTrimRecoveryIdentity` 在固定路径通过，专用维护 Docker socket 可用；真实预算代码确认取消意图并取得、续期租约，错误任务 ID 被拒。独立合成进程在 worker 和 app 的实际路径持有 flock，竞争锁被拒。该次没有执行封禁或写入核验成功回执；锁由合成进程获取，不能证明恢复 CLI 全部步骤能联动。记录 `/tmp/trim-rh-remount-fences-result.log`。模拟 app 正常停止容器后曾留下 `ActiveState=failed`；先确认进程退出、清除失败状态后才达到身份检查所需的 `inactive`，不应将 `failed` 直接视作停止安全。

真实候选源码 `recoverTrimActive.ts`（SHA-256 `4791b99c1ef75072a268a98f973ce8835cc606000c4c6289e89b7935749237cd`）在该 VM、合成数据路径和有效格式参数下实际运行，返回硬关闭错误，退出码 1；合成文件哈希未变。这只验证拒绝路径，不能代表恢复端到端通过。

待完成：目标现场完整入口和命名空间证明、实际强制或受信维护窗口验收、所有写入和崩溃阶段的恢复、与固定候选及真实账本匹配的 CLI 端到端、独立复审。当前未完成任何生产恢复或生产发布。

## 维护窗口核验器实验

`verifyTrimMaintenanceWindow.ts` 已在源码中接入恢复 CLI，但候选尚未通过独立复审和恢复端到端；只接受 root 持有的受控部署清单，检查登记的 app、quota、worker、socket、专用 daemon 等入口状态，在持有 worker/app 两把锁期间核验目标设备、可见命名空间、文件句柄及映射。函数本身不核验完整账本身份、专用维护 daemon/客户端隔离，也不自动证明全部已登记入口之外没有其他入口；将来必须与这些实际检查在同一受信窗口内组合，不能单独把它视作完整恢复屏障。

独立 VM 使用合成 ext4 和受控清单的实测：基线通过；缺失登记单元、仍活动单元、其他进程 FD、关闭 FD 后的共享映射、锁竞争、由 FD 固定但没有进程的挂载命名空间均被拒绝。网络命名空间的 nsfs 不再被错误地当作挂载命名空间；未知类型或固定挂载命名空间仍拒绝。真实 provision 创建的 root:appGid、0640 锁可通过，GID 或权限不符被拒；直接打开目标 loop 块设备、目标为不受支持设备拓扑也被拒。当前仅接受经核验的整块 loop，mapper、分区及其他设备默认拒绝。后备镜像 inode 与承载块设备纳入检查，硬链接 FD、共享映射和第二个 loop 均被拒；支持登记 mount、automount、path，已屏蔽 mount 可通过、活动 path/automount 被拒。持锁回调中串联真实身份与取消租约，子进程未继承锁；异常及 SIGKILL 后锁可再次获取。当时尚未接入恢复 CLI；现已完成源码集成但未进行恢复端到端。证据 `/tmp/trim-rh-probe-final-pass2.log`，核验器源码 SHA-256 `9e5d0811ce7c200a87622fa34c34a538aeee53f4251585e90ffb6da2d39496cd`。验证使用 VM 的真实 systemd、内核挂载及进程，非生产运行。

这是有限的时点检查：例如 SCM_RIGHTS 队列中的文件引用不能可靠通过 FD/maps 扫描看见，注册清单也不能证明未登记的自动化不存在。这些条件依赖现场受信运维确认已知服务、客户端与自动化均已停止，并在整个维护窗口禁止引入其他写者；有未知入口、未知引用或无法完成核验时继续拒绝。未来是否接入、锁持有与既有 CLI 的组合方式，以及所有崩溃点均须独立复审及真实 CLI 端到端验证。

复审后的实验核验器先拒绝 `fcntl` 负返回，回调不接收原始锁 FD；独立打开的竞争探针需返回明确 EWOULDBLOCK。VM 验证了意外解锁、关闭并替换 FD 均拒绝，异常及 SIGKILL 后锁能再次取得。底层设备 holder 与无法证明不重叠的分区要求拒绝；VM 用未挂载的独立合成 loop 加只读 dm 映射证实 sysfs 出现 holder，但在正在挂载的目标 loop 注入 dm holder 被内核以 EBUSY 拒绝，因此核验器 holder 分支尚未在完整维护窗口中实测。不能把这一项记为端到端通过。

锁身份每次与受控清单中固定的 UID、GID、权限、设备号和 inode 核对。独立 VM 对 worker 和 app 锁分别修改同一 inode 的 UID、GID，四项均拒绝，随后恢复原始属性；证据 `/tmp/trim-rh-ownership-negative-result.log`。当前仅是核验器实验，已在源码中进行同进程集成，但真实恢复端到端尚未运行。

底层分区的 `holders` 读取失败现在一律拒绝，不再把缺失解释为空；VM 真实 sysfs 存在该目录，私有命名空间模拟将该目录遮蔽后，真实核验器返回 ENOENT 并拒绝。正负例日志 `/tmp/trim-rh-holders-required-negative2.log`。

主分区及同盘 sibling 分区一旦识别到 `partition` 标记，所需 `dev`、`start`、`size` 或父设备信息读取失败均拒绝。独立 VM 在私有 namespace 遮蔽 sysfs 模拟六种缺失，均拒绝，未遮蔽正例通过；日志 `/tmp/trim-rh-partition-negative-result.log`。

集成候选在恢复源码中由维护窗口统一持有两把锁，关键操作前可重复核验；先前的硬关闭版本在独立 VM 以合成参数运行时拒绝执行，数据哈希未变。当前候选已用实际条件核验取代字面量硬关闭，两个入口的 TypeScript 独立检查与 Bun 语法构建通过；当前候选尚未执行真实恢复路径，等待独立复审。

容器终止前的租约检查已接入源码：受控 VM 中，真实 SQLite 租约有效时，实际续租辅助函数允许删除专用 daemon 的合成测试容器；将合成租约行的截止时间置为过去后，同一辅助函数拒绝动作，另一合成容器经 Docker inspect 确认仍在运行。随后仅清理该测试容器。证据 `/tmp/trim-lease-removal-result2.log`。这验证的是同一生产辅助函数和真实租约/容器，而不是恢复 CLI 端到端。
